# Happ traffic stall, 25 October 2026

All user-facing times below are Asia/Yekaterinburg (UTC+5).

## Evidence and limits

- Mac Happ 5.7.0 / embedded Xray 26.7.28 started at 15:24:49. The earlier
  continuous test at 15:35:26–15:47:49 returned 49/49 HTTP 204 responses through
  this active Happ session. It was too short to rule out the later failure.
- At 15:55:15 Happ logged `MeasureOutboundDelay Error All outbound return -1`;
  the user also reported failed websites. Fresh core start 15:56:49 still logged
  failures at 15:57:03. Later starts are present at 16:28:23 and 17:00:00, so the
  logs do not establish recovery of one uninterrupted connection.
- Independent panel probes at 15:55 successfully carried native HTTPS on all
  three transports and HTTPS plus both STUN targets through subscription
  routing (9/9). Nine monitor runs from 15:49 through 16:38 completed status 0.
  This rules out a sustained global outage during those samples, not an outage
  limited to the customer's path, account or client.
- Node container still started 22 October 07:14:39 UTC, restart count 0.
  Current tariff acknowledgement healthy, usage map empty. TLS certificate
  expires 20 December. No production core replacement or restart was performed.
- At investigation time, DNS queries from the Mac to 1.1.1.1 and 8.8.8.8 timed
  out, while router DNS resolved the node and TCP ports 443/2096 were reachable.
  The system DNS snapshot had no reachable default resolver and a scoped router
  resolver. Active Happ traffic nevertheless worked. These observations expose
  bootstrap DNS dependence; they do **not** prove DNS caused the 15:55 outage.
- Refresh of panel/subscription domains is explicitly DIRECT, so successful
  subscription refresh is not evidence of tunnel health.

## Mitigation applied

At 17:09 UTC+5 the three managed host connection addresses were changed from
`node.yanlo.biz` to the existing node IP `89.34.219.170`. All explicit SNI names,
certificates, credentials, ports and transport settings were retained. Injected
backup outbounds also use the IP. No node restart; existing sessions stay intact.
Private rollback snapshot on the panel:
`/opt/remnawave/backups/node-bootstrap-20261025T120911Z.json`.

Validation:

- Five local bootstrap tests (scope/TLS guards, failure rollback including a
  rollback error) and the existing recovery routing test pass; Ruff passes.
- Candidate IP configurations: HTTPS and two UDP/STUN targets per transport,
  **9/9 pass**. Disposable clients with each primary disabled: **9/9 pass**,
  HTTPS recovery at startup 4.3s REALITY, 0.2s XHTTP, 10.2s Hysteria.
- Published outputs: three URI endpoints and all Happ primary/backup endpoints
  have the intended IP and explicit TLS/REALITY names; existing verifier passes.
- Actual published configs, without candidate overrides: HTTPS and both STUN
  targets per transport **9/9 pass**. Disposable test accounts removed.

## Not yet established

The mitigation removes one shared dependency; it is not a demonstrated complete
fix for the reported prolonged outage. A client subscription refresh/reconnect
and a longer real Happ session spanning the failure conditions are still needed.
All fallback transports share the same node and IP, so they cannot cover an
IP/path block or a node/provider outage. Existing checks sample fresh clients;
they do not prove long-session recovery, sleep/wake or recovery of live streams.

Xray upstream has later Hysteria fixes, but replacing just the server cannot
update the embedded client core. Preserve custom device revocation and shared
tariff patches if preparing a server upgrade; do not install a stock binary over
the patched core.
